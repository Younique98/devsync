# Deployment

DevSync's real deployment target: **Vercel** (Next.js frontend, already
live) + **Fly.io** (Express backend, Postgres, Vault, Consul) +
**MongoDB Atlas** (managed Mongo, free tier). This is genuinely real
infrastructure - not self-hosted stand-ins, not localhost-only - sized for
an early-stage product without production traffic yet: every Fly service
scales to zero when idle, so cost tracks actual usage instead of paying
for always-on capacity nobody's using yet. Scaling any one piece up later
(more Fly `min_machines_running`, a bigger Postgres VM, Atlas's paid
tiers) is a config change, not a rebuild.

The one piece that is **not** a shortcut and is worth calling out
specifically: **Vault runs a real, non-dev server with AWS KMS
auto-unseal** (`fly/vault/`), the same production auto-unseal pattern
[HashiCorp documents](https://developer.hashicorp.com/vault/docs/configuration/seal/awskms)
for real secrets - not `vault server -dev`. See "Bootstrap Vault
(one-time)" below.

A note on how this doc was verified: this sandbox's network egress to
`fly.io` (and its docs/community subdomains) is blocked entirely, so every
`fly.toml` field and CLI flag below was cross-checked via web search
against Fly's documentation titles/snippets and, where that was
ambiguous, a live `superfly/flyctl` GitHub issue - not guessed from
memory, but also not click-verified against the live docs page the way it
would be with normal network access. Run `fly config validate` on each
`fly.toml` before your first real deploy of each app, and treat the "Why
Flycast" section's exact flags as needing a `--help` sanity check.

## 1. MongoDB Atlas (free M0 tier)

MongoDB is **not** self-hosted or containerized anywhere in this
deployment - `database.ts` just does `mongoose.connect(mongoUri)` against
whatever `MONGO_URI` Vault hands it, so a managed Atlas cluster is a
drop-in swap for the local docker-compose Mongo container, no code
changes required. This is manual, one-time account setup on Atlas's own
console - nothing here provisions it for you.

1. Create a free account at [mongodb.com/cloud/atlas](https://www.mongodb.com/cloud/atlas) if you don't have one.
2. **Create a cluster** → choose the **M0 Free** tier (shared RAM, 512MB storage - no card required, no expiry). Pick a cloud/region close to Fly's `iad` region (e.g. AWS `us-east-1`) to keep latency down.
3. **Database Access** → add a database user (username + password, or Atlas-managed auth) scoped to this cluster only.
4. **Network Access** → add an IP allowlist entry. Fly Machines don't have stable outbound IPs by default, so either allow `0.0.0.0/0` (acceptable for an M0 demo-traffic cluster gated by its own username/password - not something to carry into a cluster holding real customer data) or set up [Fly's dedicated egress IPs](https://fly.io/docs/networking/services/) and allowlist those specifically once traffic is real.
5. **Connect** → "Drivers" → copy the `mongodb+srv://...` connection string, filling in the database user's password.
6. That string is your `MONGO_URI` - it goes into Vault via `fly/vault/seed-vault-prod.sh`, the same way local dev's Vault gets it from `init-vault.sh` (see `.env.example`).

M0 is genuinely free forever (not a trial), durable, and Atlas-managed
(backups, patching, monitoring are Atlas's job) - appropriate for real
but low-volume traffic, not a toy. If usage ever needs more than 512MB or
dedicated resources, Atlas's paid tiers are the same connection-string
swap, no app changes.

## 2. Fly.io apps

Four independent Fly apps, each scaling to zero on its own:

| App | Config | Public? | Notes |
|---|---|---|---|
| `devsync-backend` | `fly/backend/fly.toml` | Yes (public HTTPS) | The Express API |
| `devsync-postgres-db` | generated by `fly postgres create` | No | Fly-managed Postgres |
| `devsync-vault` | `fly/vault/fly.toml` | No (Flycast only) | Real Vault, KMS auto-unseal |
| `devsync-consul` | `fly/consul/fly.toml` | No (Flycast only) | Service discovery, dev-agent |

Install `flyctl` and `fly auth login` first (see
[fly.io/docs/flyctl/install](https://fly.io/docs/flyctl/install/)).

### Why Flycast

The backend, Vault, and Consul all need scale-to-zero (`auto_stop_machines
= "stop"`, `auto_start_machines = true`, `min_machines_running = 0`). For
the backend that's straightforward - it has real public HTTP traffic, and
Fly's Proxy autostarts a stopped machine the moment a request for it
arrives.

Vault and Consul have no public traffic of their own - only the backend
talks to them, over Fly's private network. Plain `<app>.internal` (6PN)
addressing connects machine-to-machine directly and **bypasses the Fly
Proxy entirely**, which means a request to a stopped Vault/Consul machine
over `.internal` will just fail to connect instead of waking it. **Flycast**
is Fly's private-only proxy network specifically built to fix this -
private traffic still routes through the Fly Proxy, so autostart works
the same way it does for public apps. That's why `fly/vault/fly.toml` and
`fly/consul/fly.toml` have no public IP and `devsync-backend`'s
`VAULT_ADDR`/`CONSUL_ADDR` point at `*.flycast` hostnames, not
`*.internal`.

Setup (per app, once):
```sh
# From inside each app's first `fly launch`/`fly apps create`, or after:
fly ips allocate-v6 --app devsync-vault --private
fly ips allocate-v6 --app devsync-consul --private
```
(`fly launch --flycast` does this automatically at creation time instead,
if you're creating the app fresh rather than from the `fly.toml` files
here - double-check the exact flag with `fly ips allocate-v6 --help`,
since this sandbox couldn't load Fly's docs page to confirm it verbatim.)

Fly Postgres is **not** on Flycast - its own scale-to-zero (below) is a
Postgres-image-specific wake-on-connect mechanism, documented separately
from this generic Flycast requirement, and works fine over the normal
`<app>.internal` address.

### Deploy the backend
```sh
# From the repo root - build context must be the repo root (the Dockerfile
# needs package.json/yarn.lock/tsconfig*.json/*.ts at the top level), not
# fly/backend/, even though that's where fly.toml and the Dockerfile live.
fly apps create devsync-backend
fly ips allocate-v6 --app devsync-backend   # public - autostart via the normal Fly Proxy path
fly secrets set -a devsync-backend \
  VAULT_TOKEN=<the devsync-app policy token - see "Bootstrap Vault" below> \
  METRICS_TOKEN=<pick a real value, matching monitoring/prometheus.yml if you deploy that too> \
  JWT_SECRET_KEY=<pick a real value - also seeded into Vault, see below> \
  GITHUB_CLIENT_ID=<from your GitHub OAuth App> \
  GITHUB_CLIENT_SECRET=<from your GitHub OAuth App> \
  GITHUB_CALLBACK_URL=https://devsync-backend.fly.dev/auth/github/callback
fly deploy --config fly/backend/fly.toml .
```

### Provision Fly Postgres (scale-to-zero)

There is **no CLI flag** for non-interactive scale-to-zero on Postgres
creation as of this writing - confirmed against
[a live, open `superfly/flyctl` issue](https://github.com/superfly/flyctl/issues/4172)
asking for exactly that flag, not assumed. The supported path is the
interactive wizard:

```sh
fly postgres create --name devsync-postgres-db --region iad
```
Choose the **"Development"** configuration (single node, `shared-cpu-1x`,
1GB) when prompted, then answer **yes** to *"Scale single node pg to zero
after one hour of inactivity?"*. That sets `FLY_SCALE_TO_ZERO = "1h"` in
the generated Postgres app's own `fly.toml` automatically - there's
nothing to hand-write here, which is why there's no `fly/postgres/`
directory in this repo. If you ever need to check or change it:
```sh
fly config save -a devsync-postgres-db      # pulls its fly.toml locally
# confirm [env] has: FLY_SCALE_TO_ZERO = "1h"
fly deploy -a devsync-postgres-db           # after any edit
```
One hour is currently the only supported timeout (not configurable) -
after an hour with no open connections the database machine stops; the
next connection attempt restarts it, with the connecting client (Vault
seeding, or the backend's own `pg.Pool`) seeing that first-connection
delay.

Create the app's Postgres user/database and get its internal hostname:
```sh
fly postgres connect -a devsync-postgres-db
# inside psql:
CREATE USER devsync_app WITH PASSWORD '<pick a real password>';
CREATE DATABASE devsync OWNER devsync_app;
```
The host to hand to Vault (`PG_HOST` below) is the app's own internal
name, e.g. `devsync-postgres-db.internal`.

Run migrations once Vault (below) is seeded and the backend can reach
Postgres - `npm run migrate` needs `PG_HOST`/`PG_USER`/`PG_PASSWORD`/
`PG_DATABASE` in its own environment (it doesn't go through Vault - see
`migrations/migrate.js`), so run it via `fly ssh console -a
devsync-backend` or from a machine with a `fly proxy` tunnel open.

### Bootstrap Vault (one-time)

This is the one genuinely different piece from a typical Fly deploy: a
real Vault server starts **sealed and uninitialized** the first time,
and stays sealed on every restart until unsealed. AWS KMS auto-unseal
(`fly/vault/vault-config.hcl`) makes every restart *after* this bootstrap
automatic - but the bootstrap itself is a one-time manual sequence.

**a. Create the KMS key first** (Vault needs it to exist before it can
init against it):
```sh
aws kms create-key --description "devsync-vault auto-unseal" --region us-east-1
aws kms create-alias --alias-name alias/devsync-vault-unseal \
  --target-key-id <KeyId from above> --region us-east-1
```
Create a narrowly-scoped IAM user (or role) whose policy allows only
`kms:Encrypt`, `kms:Decrypt`, and `kms:DescribeKey` on that one key ARN -
not a broad AWS admin credential. Cost: KMS charges ~$1/month per key plus
a few cents per 10,000 API calls - at demo/early traffic (Vault only calls
KMS on cold starts, i.e. once per scale-to-zero wake) this lands around
**$1-3/month**, not the $0 everything else here mostly costs.

**b. Deploy Vault and initialize it:**
```sh
fly apps create devsync-vault
fly ips allocate-v6 --app devsync-vault --private   # Flycast - see above
fly secrets set -a devsync-vault \
  VAULT_AWSKMS_SEAL_KEY_ID=alias/devsync-vault-unseal \
  AWS_ACCESS_KEY_ID=<the scoped IAM user's key> \
  AWS_SECRET_ACCESS_KEY=<the scoped IAM user's secret>
fly deploy --config fly/vault/fly.toml .

fly proxy 8200 -a devsync-vault    # in one terminal, leave running
# in another terminal:
export VAULT_ADDR=http://localhost:8200
vault operator init -key-shares=1 -key-threshold=1
```
`vault operator init` against an `awskms`-sealed Vault auto-unseals
immediately using the KMS key - there's no `vault operator unseal` step
and no Shamir key shares to distribute to unseal it (init still prints
"Recovery Key" material; save that somewhere safe like a password manager
for rare recovery operations, but it's not needed for routine restarts).
It also prints the **initial root token** - that authenticates the next
step.

**c. Seed real secrets and create the app's actual (non-root) token:**
```sh
export VAULT_TOKEN=<the root token from vault operator init>
PG_USER=devsync_app \
PG_PASSWORD=<the password you set on Postgres above> \
PG_DATABASE=devsync \
PG_HOST=devsync-postgres-db.internal \
MONGO_URI=<your Atlas connection string> \
JWT_SECRET_KEY=<pick a real value> \
  ./fly/vault/seed-vault-prod.sh
```
The script prints a `vault token create` command - run it, then
`fly secrets set VAULT_TOKEN=<that token> -a devsync-backend`. That's the
token the running backend actually uses day to day (read-only on exactly
`secret/data/database` and `secret/data/auth` - see
`fly/vault/devsync-app-policy.hcl`); the root token goes into a password
manager for break-glass use, not into any `fly secrets set`.

After this, every future cold start - the backend waking Vault via
Flycast, or Vault restarting for any other reason - auto-unseals with no
manual step, because the KMS key (not a human) holds what's needed to
unseal it.

### Deploy Consul
```sh
fly apps create devsync-consul
fly ips allocate-v6 --app devsync-consul --private   # Flycast - see above
fly deploy --config fly/consul/fly.toml .
```
Nothing to seed - `serviceDiscovery.ts` registers the backend's own
service entry on startup and deregisters it on shutdown, so Consul's
catalog rebuilds itself every time it cold-starts, the same as it does
today on every local `docker-compose up`.

## 3. Point Vercel at the Fly backend

In the Vercel project's **Settings → Environment Variables**, set:
```
NEXT_PUBLIC_BACKEND_URL=https://devsync-backend.fly.dev
```
then redeploy the frontend (Vercel env var changes need a redeploy to
take effect in the built output, since `NEXT_PUBLIC_*` vars are inlined at
build time).

**Honesty check on this step:** as of this deployment pass, no frontend
code actually *reads* `NEXT_PUBLIC_BACKEND_URL` at runtime yet -
`pages/dashboard.tsx` renders `lib/mockData.ts` (static demo data), not a
live fetch against the backend. Setting the Vercel env var now is still
the correct move (it's already documented as the frontend↔backend
contract in `.env.example`, and costs nothing to have set), but it won't
visibly change anything in the deployed frontend until a live fetch is
added. See the next section.

## 4. Cold starts and the dashboard (follow-up, not built this pass)

Waking a scaled-to-zero Fly machine typically takes low single-digit
seconds; the backend's own cold start can compound with Vault's and
Postgres's if they're *also* asleep (a fully cold path: backend wakes →
calls Vault over Flycast, which wakes → Vault calls Postgres, which
wakes → connections succeed). Worth knowing about, not a bug - this is
the real tradeoff of paying for zero idle capacity instead of always-on.

I checked whether there's a cheap, low-risk place to add a "waking up
demo infrastructure..." style message for this, per the request - there
isn't one *yet*, honestly: `pages/dashboard.tsx` has no live loading
state to begin with, because it renders `lib/mockData.ts` directly with
no `fetch()` call (see grep results above - `NEXT_PUBLIC_BACKEND_URL`
isn't consumed anywhere in `pages/`/`components/`/`lib/` today). Adding a
real loading/cold-start-aware state means first wiring an actual live
data fetch, which is a bigger change than fits this deployment pass and
is really its own feature (swapping the dashboard from demo data to a
real `/admin/status`-style call). Flagging it here as the natural
follow-up: whoever wires that fetch should reuse the pattern this repo
already leans on elsewhere (`StatusPill`, `Seo`) and add a
"waking up demo infrastructure…" state for the case where that fetch is
still pending after ~1-2s, rather than just showing a bare spinner or
(worse) a blank/broken-looking tile grid.

## 5. Cost summary

| Piece | Tier | Cost |
|---|---|---|
| Vercel (frontend) | Hobby | $0 |
| MongoDB Atlas | M0 free | $0 |
| Fly `devsync-backend` | `shared-cpu-1x`/512MB, scale-to-zero | ~$0 idle, pennies per active-hour |
| Fly Postgres | Development single-node, scale-to-zero (1hr) | ~$0 idle + ~1GB volume (~$0.15/mo) |
| Fly `devsync-vault` | `shared-cpu-1x`/512MB, scale-to-zero + small volume | ~$0 idle + volume |
| Fly `devsync-consul` | `shared-cpu-1x`/256MB, scale-to-zero | ~$0 idle |
| AWS KMS (Vault auto-unseal) | 1 key | ~$1/mo + ~$0.03 per 10k requests |

At occasional-demo traffic this whole stack should land in the low single
digit dollars per month - the KMS key is the only genuinely fixed line
item; everything else tracks actual usage. Fly's free allowances change
over time, so treat the table above as order-of-magnitude, not a quote -
check Fly's current pricing before committing.

## What's verified vs. not

- **Verified**: all three `fly.toml` files parse as valid TOML
  (`tomllib.load` in this sandbox). The `auto_stop_machines`/
  `auto_start_machines`/`min_machines_running` fields, the `[http_service]`/
  `[[vm]]`/`[[mounts]]` shapes, and Flycast's `.flycast` hostname + `--private`
  IP allocation were all cross-checked against multiple current examples
  and Fly's own doc page *titles* via web search (direct fetches of
  `fly.io` and its subdomains are blocked from this sandbox's network).
  Fly Postgres's lack of a non-interactive scale-to-zero flag was
  confirmed against a live, open `flyctl` GitHub issue, not assumed. The
  `seal "awskms"` stanza and its env vars (`VAULT_AWSKMS_SEAL_KEY_ID`,
  `AWS_REGION`, standard AWS credential env vars) were cross-checked
  against HashiCorp/OpenBao doc snippets the same way.
- **Not verified - genuinely needs Erica to run it**: no `fly deploy` was
  run anywhere (no Fly account/credentials in this sandbox), and Docker's
  daemon isn't available in this sandbox either (`docker build` fails with
  "no such file or directory" on the socket - the client binary is
  present but nothing's running), so none of the three Dockerfiles here
  have been build-tested. They're syntactically ordinary multi-stage
  Docker/Vault/Consul images with nothing exotic in them, but "looks right
  on inspection" is not the same as a real `docker build`/`fly deploy` -
  do both, and watch the logs, before treating this as live.
- Vault's bootstrap sequence (`vault operator init` against a real
  `awskms` seal) is written to Vault's documented, standard pattern, but
  wasn't run against a real Vault + real AWS KMS key from this sandbox
  either - no AWS credentials available here.
